# 履歷回饋整理

## 整體問題

Summary 是履歷最先被看見的區域。HR 通常會先看 Summary 和 Skills，之後才看工作經歷，因此履歷大約只有十秒能抓住對方的注意力。

目前的個人敘述過於薄弱，只交代了做過哪些工作，卻沒有清楚呈現改善了什麼、創造了哪些商業價值，以及能承擔多少責任。薪資能開到哪裡，最終仍取決於實力、可承擔的責任範圍，以及公司的招募預算。

「從零到一建置產品」、「將複雜需求拆解為可執行方案」等說法已經相當普遍；技術評估本來也是工程師的基本能力，因此難以形成差異化。「交付兼具工程嚴謹性與商業價值的高品質解決方案」也需要改寫，在強調快速驗證的 MVP 文化中，這種表述甚至不一定是優點。

「建立工程規範與協作流程」同樣過於空泛。Signature Work 與 Experience 的內容高度重複，等於用履歷中最重要的版位，先把後面的內容再講一次較淡的版本。Summary、Skills 與 Signature Work 三者目前不但沒有互相加強，反而彼此稀釋。

## 經歷與版面問題

「雲端達人」之下列了兩段 Software Engineer 經歷，但 2022 年那一段沒有標示公司名稱，時間軸中間也出現半年以上的空窗，建議補充或說明。

Skills 應依能力領域分組。若只在每段工作經歷下羅列使用過的工具，就會變成工具名稱流水帳。會使用哪些工具，與能夠承擔哪些責任，是兩件不同的事。

## 成果必須具體且可驗證

「顯著降低 Bug 發生率」缺乏必要的背景與證據，例如：

- 專案規模多大？
- 是否有 Bug Tracker 的紀錄？
- 重構前後的 Bug 數量各是多少？
- 統計涵蓋的時間與範圍為何？

履歷可以加入實際成果數字，但任何數字都必須有足夠的驗證方式。修改時，建議把 Summary 留到最後，先深入整理工作經歷與 Signature Work。

以「拆分 UI 業務邏輯與資料層」為例，應補充專案規模、頁面數量，以及拆分前的混亂程度。可以朝以下方式描述：

> 在具有 160 個頁面的支付系統中，透過特定方法將原有架構拆分為明確模組，降低團隊協作與問題排查成本，並提升可被驗證的開發效率。

任何百分比都必須能說明分子、分母、測量方式及適用範圍。若寫下「提升 30%」，面試官很可能追問計算方式，因此不需要為了好看而硬湊數字。

## 將日常工作轉換成有價值的敘事

「推動固定頻率的 Stand-up Meeting」不適合直接當成成果，因為面試官可能將它解讀為團隊成熟度不足。除非背後有一段能說明問題、行動與成果的完整故事。

例如，若遠端成員失聯曾導致交付出現問題，可以改寫成「重建團隊資訊同步機制」，並交代事件背景、採取的措施，以及改善後的成果。

「部門協調與問題管理」也只是工作描述。若要保留，應補上具體敘事，否則可能讓人認為公司原本缺乏制度。

## 強化金流產業經驗

藍新屬於受監管的支付金流單位，因此資安補強是一個值得深入呈現的方向。在金流公司處理冪等性、金額精度與資安審查，對雇主而言，通常比「主導某系統的前端模組化」更有分量，應善用這些產業經驗凸顯自身價值。

## 招募市場觀察

目前外部招募預算比去年低，市場主要尋找兩類人才：

- 願意接受較低薪資的中高階人才。
- 年資較淺、但能力接近中階的人才。

預估招募市場要到十月後才會逐步回溫。

## 重點總結

- 先深化 Experience 與 Signature Work，最後再重寫 Summary。
- Summary、Skills 與 Signature Work 應各自發揮不同作用，避免內容重複。
- 少用「從零到一」、「拆解複雜需求」等缺乏差異化的常見表述。
- 描述成果時要交代專案規模、原始問題、採取的方法及最終影響。
- 所有數據與百分比都要有可說明、可驗證的計算依據。
- Skills 應按能力領域整理，不要只羅列工具。
- 補齊公司名稱及履歷空窗等時間軸資訊。
- 不要把例行會議或基礎流程直接包裝成成果，應呈現背後解決的問題。
- 優先強調金流領域中的冪等性、金額精度、資安與監管經驗。
- 薪資取決於可承擔的責任、實際能力及市場預算。

## 名詞註釋

- **Summary（個人摘要）**：履歷開頭的簡短自我介紹，用來快速呈現專業定位、核心能力與主要價值。
- **Skills（技能）**：依能力領域整理的專業技能，例如前端架構、測試、雲端或團隊協作，不應只是工具清單。
- **Signature Work（代表作品／代表成果）**：最能證明個人能力與影響力的專案或成果。
- **冪等性（Idempotency）**：同一操作執行一次或多次，最終結果保持一致的特性；在付款重試與防止重複扣款中特別重要。
- **金額精度**：確保貨幣計算、儲存及顯示不因浮點誤差而產生錯誤的處理要求。
- **資安審查**：針對系統的存取控制、資料保護、漏洞與法規遵循進行安全檢視。
- **支付金流**：處理付款、收款、退款、對帳及資金移轉等流程的系統與服務。

## 原始對話

> 以下保留原始對話的內容與順序，僅移除說話者、時間及多餘行號。

Summary 是個第一眼看到的範圍，可是你的個人敘述每一段都太薄弱，貢獻很難知道改善了什麼，商業價值是什麼，比較像是交代工作內容。

HR 首要先看 Summary 和 Skills 後才會看到工作經驗，只有 10 秒要搏眼球。

薪資開在哪還是要看硬底子到哪，目前能接下多少責任以及對方預算。

零到一的產品建置這種話已經爛大街了，複雜需求拆解為可執行的方案也是，技術評估本就是工程師基本素養。

「交付兼具工程嚴謹性與商業價值的高品質解決方案」，在 MVP 文化比較重的公司不一定是好事。這邊要換句話說。

「工程規範與協作流程建立」那邊也幾乎等於沒說。

Signature Work 跟 Experience 幾乎是同一鍋湯裡的水。用履歷最貴的版位把後面的內容先講一次淡的版本，這裡其實馬上就被刷掉了，跟你同個狀況的競爭者應該數不完。

雲端達人下面掛了兩段 Software Engineer，我看到 2022 那裡是沒有公司名稱的，中間也有半年多的空窗。

Skills 是按能力領域分組，寫在每個工作經歷下面就是工具名稱的流水帳。

你會什麼，和可以扛什麼責任，不是同一件事。

「顯著降低 Bug 發生率」，那到底是多少規模下的前提？有 Bug Tracker 的數據嗎？重構前後各多少？

這可以加上一些你實際的成果數字，有數字就必須有足夠的驗證方法可以佐證。

Skills、Signature 和 Summary 現在三者都在互相稀釋。

要修改的話，把 Summary 放最後處理，先把工作經歷和 Signature 挖深一點。

比如 UI 業務邏輯和資料層拆分，那專案規模多大、多少頁面規模、拆之前它大概多混沌？

像是：「支付系統 160 個頁面，將 OO 利用 OOO 的方式拆為 OOO，減少團隊協作排查成本，增進 any% 效率。」

任何百分比都必須能寫出分子、分母、測量方式，以及範圍。要是你寫了 30%，那面試官也會問那怎麼算的，不用硬湊。

「推動固定頻率的 Stand-up Meeting」這個其實不需要直接暴露，把團隊成熟度低的基本盤當成果，馬上就會被面試官抓包；可行的前提是背後有一組故事。

假如遠端有人失聯導致你們交付出問題，你可以寫成重建團隊同步資訊機制。

「部門協調與問題管理」這邊也是純描述。要挖的話，你也需要準備具體敘事，不然這些會被當成公司沒有制度。

你們藍新是受監管會監理的支付金流單位，關於資安的補強議題也是一種方向。

在金流公司裡面處理冪等、金額精度、資安審查這種東西，對於資方來說，和「主導某系統的前端模組化」重量不是同一回事。這點要好好利用。

還是那句話，你現在多少 Pay 我不知道，外頭現在的招募預算比去年低很多，主要目標是找願意領低薪的中高階，以及年紀輕但有可能稍微強一點、接近中階的新鮮人。

十月起才會慢慢回溫。
